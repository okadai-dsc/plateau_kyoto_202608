# Kyoter — 分担と受け渡し

## 1. 分担

| 担当 | 範囲 | ブランチ | worktree |
|---|---|---|---|
| **Codex** | バックエンド（`backend/`） | `feature/backend` | `../kyoter-backend` |
| **Claude** | フロントエンド（`frontend/`） | `feature/frontend` | `../kyoter-frontend` |

### なぜこの割り当てか

- **バックエンド → Codex**: 仕様が完全に確定していて機械的。添字計算とスキーマ準拠が中心で、
  企画意図の解釈がほとんど要らない
- **フロントエンド → Claude**: 「地図を出さない」「歩く間は画面を見せない」など、
  **企画意図の解釈が要る**。SPEC 全体の文脈が効く

### なぜコンフリクトしないか

触るディレクトリが完全に分かれている。接点は [API.md](API.md) の JSON スキーマ1枚だけ。

```
backend/    ← Codex のみ
frontend/   ← Claude のみ
mock/       ← 双方が読む（変更しない）
docs/       ← 変更する場合は要相談
```

## 2. 開始手順

### バックエンド（Codex）

```bash
cd ../kyoter-backend
```

渡すプロンプト:

> `docs/SPEC.md`（企画）、`docs/API.md`（共通契約・必読）、`docs/BACKEND.md`（作業指示）を読んで、
> `backend/` を実装してください。`docs/BACKEND.md` の「完了の目安」を満たすことがゴールです。
> `mock/grid.json` と `mock/route.json` と同じ形のレスポンスを返すこと。
> `docs/API.md` は共通契約なので変更しないでください。

### フロントエンド（Claude）

```bash
cd ../kyoter-frontend
```

渡すプロンプト:

> `docs/SPEC.md`（企画）、`docs/API.md`（共通契約・必読）、`docs/FRONTEND.md`（作業指示）を読んで、
> `frontend/` を実装してください。`docs/FRONTEND.md` の「完了の目安」を満たすことがゴールです。
> バックエンドは未完成なので `mock/grid.json` と `mock/route.json` を読んで開発すること。
> `docs/API.md` は共通契約なので変更しないでください。

---

## 3. 守ってもらうこと

| # | ルール | 理由 |
|---|---|---|
| 1 | **`docs/API.md` を勝手に変更しない** | 変えると相手の作業が壊れる。変更が必要なら双方に共有してから |
| 2 | **`mock/*.json` を勝手に変更しない** | 同上。再生成が必要なら `tools/gen_mock.py` を使う |
| 3 | **相手のディレクトリを触らない** | `backend/` と `frontend/` |
| 4 | **通り名をハードコードしない** | 仮名（`A通`/`1通`）。実データは後で差し替える |
| 5 | **通りの本数をハードコードしない** | 実データでは本数が変わる |
| 6 | **緯度経度を使わない** | v1 のスコープ外（SPEC 4.6） |
| 7 | **地図ライブラリを使わない** | 地図を出した瞬間に企画が死ぬ（SPEC 1章） |

## 4. 仮データについて

`tools/gen_mock.py` が全ての仮データを生成する。

```bash
python3 tools/gen_mock.py
```

| 生成物 | 用途 |
|---|---|
| `mock/grid.json` | `GET /api/grid` のモック（フロント用） |
| `mock/route.json` | `POST /api/route` のモック（フロント用） |
| `backend/app/data/streets.json` | 通りの定義 ★差し替え対象 |
| `backend/app/data/exists.json` | 実在マスク ★差し替え対象 |
| `backend/app/data/visible.json` | タワー可視性 ★差し替え対象 |

### 仮データの中身

- 縦 12本（`A通`〜`L通`）× 横 16本（`1通`〜`16通`）＝ 交差点 192
- うち実在 176（通り抜け不可の街区と、途中で途切れる通りを再現）
- うちタワー可視 36（実在の 20%）

**タワーが立つ縦の通り（`ns-05`）の可視率を高くしてある。**
実際の京都で烏丸通の南北ビスタからタワーが見えるのを模したもの。
これにより経路選択ロジックの検証ができる。

`mock/route.json` の2経路がその効果を示している。

| 経路 | 内容 | 可視率 |
|---|---|---|
| `r1` | タワーの通り沿いに先に北上 | **0.88** |
| `r2` | 先に東へ折れる | 0.12 |

同じ距離・同じ曲がり回数でも、**可視率が大きく違う**。ここが本企画の技術的な核。

> 実データ（SPEC 4.8）が届いたら `backend/app/data/*.json` を差し替える。
> それ以外のコードは変更不要であること。
