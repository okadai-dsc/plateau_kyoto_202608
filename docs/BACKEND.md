## 0. このドキュメントの範囲

Python で以下を作る。

- グリッド（通りの並び）の定義とデータ
- 現在地・目的地から経路を分解するロジック
- 京都語の指示文の生成
- 上記を返す HTTP API

**やらないこと:** 画面（フロント担当）、PLATEAU の可視領域計算（外部提供・SPEC 4.8）

---

## 1. 大原則

### 1.1 通り名に依存するコードを書かない

すべて `index` で計算する。名前は表示の直前にだけ使う。

実際の京都の通り名は**まだ確定していない**。`A通` `1通` という仮名で開発し、
最後にデータファイルを差し替えるだけで本番になる状態にすること。

### 1.2 本数が変わっても壊れないこと

仮のグリッドは 12 × 16（API.md 5.2）だが、**ハードコードしない。**
実データでは本数が変わる。

### 1.3 緯度経度を使わない

座標は v1 のスコープ外（SPEC 4.6）。

## 4. 実装するもの

### 4.1 grid.py — グリッド

- `streets.json` / `exists.json` を読む
- `id ⇄ index` の相互変換
- `exists(intersection) -> bool`
- 添字の範囲チェック

### 4.2 landmark.py — 目印の可視性と方位

#### 可視性

L1〜L3（タワー・大文字・稜線）は `visible.json` を引くだけ。
計算はしない（外部提供データ・SPEC 4.8.2）。

```python
tower_visible(intersection) -> bool
```

**L4「大きい通り」だけは例外で、その場で計算する**（SPEC 2.4）。
可視データを使わず、通りの `major` フラグ・`pos`・交差点の実在マスクだけで確定する。

```python
nearest_major_street(ns_index, ew_index, max_distance=1200) -> dict | None
```

いちばん近い大通りとその方角・距離を返す。見通し判定は
**大きい通りとの交点だけ**を検査する（細い通りが届いていないことと、
見通す側が分断されていることは別物のため）。

#### 方位（8方位）

**データ不要。添字の比較だけで出す**（SPEC 4.8.3）。

```
タワー: ns-05 × ew-15
現在地: ns-02 × ew-11

ns: 5 > 2  → タワーは西    （ns の添字は東→西に増える）
ew: 15 > 11 → タワーは南   （ew の添字は北→南に増える）
⇒ 南西
```

同じ通り上にいる場合（差が 0）は単一方位になる。両方 0 の場合はタワーの足元。

```python
tower_bearing(intersection) -> Bearing
```

### 4.3 router.py — 経路の分解

グラフ探索は**しない**（SPEC 3.5）。添字の差分を取るだけ。

```
from: ns-05 × ew-11
to:   ns-02 × ew-07

ns: 5 → 2  差 -3  → 東入ル × 3
ew: 11 → 7 差 -4  → 上ル   × 4
```

#### 経路候補の生成

「上ル」と「東入ル」の**実行順序は自由**。複数パターンを作って良い順に並べる。

- 最小構成: 2通り（縦から先 / 横から先）＝ `turns` が最小になる形
- 余裕があれば途中で折り返す経路も候補に入れてよい

#### 並べ替えの基準

```
score = w1 * visible_ratio - w2 * turns
```

- `visible_ratio` = 経路上でタワーが見える交差点の割合
- `turns` = 曲がる回数（少ないほど良い）
- **重みは未決**（SPEC 6章）。定数として切り出し、後で調整できるようにする

> **なぜ可視性で選ぶのか:** ユーザーはタワーで方角を知る。
> 見えない経路を通ると方向を見失う。ここが本企画の技術的な核（SPEC 3.5）。

#### 通れない交差点

`exists` が false の交差点は通らない。経路がどうしても作れない場合はエラーを返す。

### 4.4 instruction.py — 指示文の生成

**表示用の日本語文はバックエンドで完成させる**（API.md 3.2）。フロントで組み立てさせない。

#### 文の構成

```
{方位の手がかり}、{本数}本{方向}（{到達する通り}まで）
```

例:

```
京都タワーを背にして、4本上ル（8通まで）
8通を右手に3本東入ル（C通まで）
```

#### 方位の手がかり

タワーが見える場合、**方角ではなくタワー基準の言い方にする**（SPEC 2.1）。
ユーザーに方位を意識させないため。

| 進行方向とタワーの関係 | 言い方 |
|---|---|
| タワーが進行方向の逆 | 「京都タワーを背にして」 |
| タワーが進行方向 | 「京都タワーに向かって」 |
| タワーが右 | 「京都タワーを右手に見て」 |
| タワーが左 | 「京都タワーを左手に見て」 |

タワーが見えない場合はこの句を省く（v1 では代替ランドマークを使わない・SPEC 2.4）。

#### 本数と通り名を両方出す

「3本上ル」だけだと1本ミスで詰む。**到達する通り名を必ず併記する**（SPEC 決定事項1）。
ユーザーが現地の標識で自己検証・復帰できるようにするため。

### 4.5 main.py — API

[API.md](API.md) 3章のエンドポイントを実装する。

| メソッド | パス | 優先度 |
|---|---|---|
| GET | `/api/grid` | 高 |
| POST | `/api/route` | 高 |
| POST | `/api/arrival` | 低（後回し可） |

CORS を有効にすること（フロントが別ポートから叩くため）。

## 5. データファイル（仮）

### streets.json

```json
{
  "ns": [
    { "index": 0, "name": "A通" },
    { "index": 1, "name": "B通" }
  ],
  "ew": [
    { "index": 0, "name": "1通" },
    { "index": 1, "name": "2通" }
  ],
  "tower": { "ns": 5, "ew": 15 }
}
```

仮データは ns 12本（A〜L）、ew 16本（1〜16）。

### exists.json

```json
{ "exists": [[true, true, false], [true, true, true]] }
```

`exists[ew_index][ns_index]`。**仮データでは数箇所を意図的に false にする**
（フロントの絞り込み処理を検証させるため）。

### visible.json

```json
{ "visible": [[true, false, false], [true, true, false]] }
```

同じ添字順。仮データは**タワーが立つ縦の通り（ns-05）の可視率を高く**しておくと、
実際の京都（烏丸通の南北ビスタからタワーが見える）に近い挙動になり、
経路選択ロジックの検証になる。
