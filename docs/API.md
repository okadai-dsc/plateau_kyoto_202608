# Kyoter — 共通契約（API / データモデル）

> **このファイルはフロント・バック双方が読む唯一の契約。**
> 片方だけで変更しない。変更する場合は必ず両者に共有する。
>
> 前提となる企画・仕様は [SPEC.md](SPEC.md) を参照。

---

## 0. 大原則

### 0.1 通り名はただのラベル。ロジックは添字で動く

**通り名に依存する処理を書かないこと。** すべて `index` で計算する。

これにより、実際の京都の通り名（烏丸通・四条通…）が確定していなくても
v1 の全機能が完成させられる。最後に名前テーブルを差し替えるだけでよい。

### 0.2 v1 は緯度経度を一切使わない

座標フィールドは契約に存在しない。GPS も地図も使わない。

## 1. 座標系（グリッド）

京都の碁盤の目を、2本の軸の**添字**で表す。

| 軸 | 意味 | 添字の向き | 仮の表示名 |
|---|---|---|---|
| `ns` | 南北に走る通り（縦） | **0 = 最も東**、増えるほど西 | `A通`, `B通`, `C通` … |
| `ew` | 東西に走る通り（横） | **0 = 最も北**、増えるほど南 | `1通`, `2通`, `3通` … |

> 添字の向きは京都の数え歌の順（北→南 / 東→西）と一致させてある。
> 実データを入れる際もこの順を守ること。

### 1.1 方向と添字の対応

| 表記 | 方角 | 添字の変化 |
|---|---|---|
| `上ル` | 北 | `ew_index - 1` |
| `下ル` | 南 | `ew_index + 1` |
| `東入ル` | 東 | `ns_index - 1` |
| `西入ル` | 西 | `ns_index + 1` |

## 2. 型定義

### 2.1 Street

```json
{
  "id": "ns-12",
  "axis": "ns",
  "index": 12,
  "name": "烏丸通",
  "major": true,
  "pos": 840,
  "width": 25
}
```

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | `"{axis}-{index:02d}"`。安定した識別子 |
| `axis` | `"ns"` \| `"ew"` | 軸 |
| `index` | int | 0 始まり。1章の向きに従う |
| `name` | string | **表示専用。**ロジックで使わない |
| `major` | bool | 主要な通りか。**表示専用** |
| `pos` | int | 基準の通りからの距離(m)。`ns` は最も東の通りから西へ、`ew` は最も北の通りから南へ。**表示専用** |
| `width` | int | 通りの幅(m)。**表示専用** |

> `pos` / `width` は**グリッドの見た目を実際の街の比率に合わせるため**だけに使う。
> 隣り合う `pos` の差が街区の広さ、`width` が罫線の太さになる。
> 経路計算は添字で行うので、これらの値はロジックに影響しない。
>
> これは緯度経度ではなく、通り同士の相対的な距離。v1 が座標を持たない方針
> （SPEC 4.6）は保たれている。

### 2.2 Intersection

```json
{ "ns": "ns-03", "ew": "ew-07" }
```

南北の通りと東西の通りの組。これだけで位置が一意に決まる。

### 2.3 Direction

```
"上ル" | "下ル" | "東入ル" | "西入ル"
```

### 2.4 Bearing（8方位）

```
"北" | "北東" | "東" | "南東" | "南" | "南西" | "西" | "北西"
```

京都タワーがどちらに見えるかを表す。添字の比較のみで算出する（SPEC 4.8.3）。

## 3. エンドポイント

ベースパス: `/api`

### 3.1 `GET /api/grid`

グリッドの定義を返す。フロントは起動時に1回だけ呼ぶ。

**レスポンス**

```json
{
  "ns_streets": [
    { "id": "ns-00", "axis": "ns", "index": 0, "name": "A通" },
    { "id": "ns-01", "axis": "ns", "index": 1, "name": "B通" }
  ],
  "ew_streets": [
    { "id": "ew-00", "axis": "ew", "index": 0, "name": "1通" },
    { "id": "ew-01", "axis": "ew", "index": 1, "name": "2通" }
  ],
  "exists": [
    [true,  true,  false],
    [true,  true,  true ]
  ],
  "tower": { "ns": "ns-12", "ew": "ew-24" },
  "spots": [
    {
      "name": "錦市場",
      "at": { "ns": "ns-02", "ew": "ew-11" }
    },
    {
      "name": "京都御苑",
      "at": { "ns": "ns-02", "ew": "ew-01" },
      "area": { "ns": ["ns-02", "ns-12"], "ew": ["ew-00", "ew-01"] }
    }
  ]
}
```

| フィールド | 説明 |
|---|---|
| `ns_streets` | 南北の通り。`index` 昇順（東→西） |
| `ew_streets` | 東西の通り。`index` 昇順（北→南） |
| `exists` | **実在マスク。**`exists[ew_index][ns_index]` が `false` なら交差点が存在しない |
| `tower` | 京都タワーが立つ交差点 |
| `spots` | グリッド上に表示する観光地。**表示と目的地選択の補助にのみ使う** |

#### Spot

| フィールド | 型 | 説明 |
|---|---|---|
| `name` | string | 観光地名 |
| `at` | Intersection | 代表する交差点。**必ず実在する交差点** |
| `area` | object? | 敷地の広がり（任意）。`ns` / `ew` はそれぞれ両端の street id |

> 観光客が行きたいのは「三条 × 河原町」ではなく「錦市場」なので、
> 通り名を知らなくても目的地を選べる入口として使う（SPEC 4.5.3）。

> `exists` の添字順に注意。**行 = ew（横の通り）、列 = ns（縦の通り）** で、
> 画面上の見た目と一致する。

### 3.2 `POST /api/route`

現在地と目的地から、経路候補と指示文を生成する。

**リクエスト**

```json
{
  "from": { "ns": "ns-05", "ew": "ew-11" },
  "to":   { "ns": "ns-02", "ew": "ew-07" }
}
```

**レスポンス**

```json
{
  "from": { "ns": "ns-05", "ew": "ew-11" },
  "to":   { "ns": "ns-02", "ew": "ew-07" },
  "start": {
    "tower_visible": true,
    "tower_bearing": "南",
    "hint": "京都タワーが南に見えます。タワーを正面に見て、真後ろが上ルです。"
  },
  "moves": [
    {
      "direction": "上ル",
      "count": 4,
      "to_street": "ew-08",
      "to_street_name": "三条通",
      "instruction": "三条通まで上ル（およそ4本）"
    },
    {
      "direction": "西入ル",
      "count": 11,
      "to_street": "ns-12",
      "to_street_name": "烏丸通",
      "instruction": "烏丸通まで西入ル（およそ11本）"
    }
  ]
}
```

#### moves

**経路は返さない。**返すのは「方角 × 本数」だけ（SPEC 3.5）。

碁盤の目では 上ル/下ル と 東入ル/西入ル を**どの順に消化しても着く**ので、
覚えるのは方角2つと本数2つで足りる。順番まで決めると普通のナビになり、
この企画の一番の良さが消える。

要素は最大2つ（同じ通り上なら1つ）。

| フィールド | 型 | 説明 |
|---|---|---|
| `direction` | Direction | `上ル` / `下ル` / `東入ル` / `西入ル` |
| `count` | int | **目安の本数。**通り順（数え歌の並び）での差 |
| `to_street` | string | 到達する通りの `id` |
| `to_street_name` | string | 到達する通りの表示名 |
| `instruction` | string | 表示用の完成した日本語文 |

> **本数は目安。通り名が正。**
> 実際に横切る本数は通る道で変わる（届いていない小路があるため）。
> 順番を決めない以上ひとつに定まらないので、通り名で答え合わせできるようにしてある。

#### start

目印は**経路を選ぶためではなく、どちらが上ルかを知るため**にある。

```json
{
  "landmark": {
    "id": "daimonji",
    "name": "大文字",
    "layer": 2,
    "bearing": "北東",
    "distance": 3605
  },
  "hint": "大文字が北東に見えます。大文字を正面に見て、左前が上ルです。"
}
```

| フィールド | 説明 |
|---|---|
| `landmark` | その交差点から使える**いちばん精度の高い目印**。ひとつも無ければ `null` |
| `landmark.kind` | `point` / `skyline` / `street`。下表参照 |
| `landmark.layer` | 小さいほど精度が高い（L1=京都タワー、L2=大文字、L3=稜線、L4=大きい通り） |
| `landmark.bearing` | 8方位。**近すぎて方角に使えない場合は `null`** |
| `landmark.distance` | 目印までの距離(m)。`kind` が `skyline` のときは代わりに `walk` |
| `landmark.azimuth` | **8方位に丸める前の正確な方位(度)。北=0、東=90。図に置くときはこちら** |
| `landmark.azimuth_from` | 目印が占める範囲の左端(度) |
| `landmark.angular_width` | **見かけの角幅(度)。**単独峰は山塊の幅から、連なりは両端から |
| `landmark.elevation` | **見かけの高さ（仰角・度）** |
| `landmark.height` | 目印の高さ(m)。`peak` / `range` は標高、`point` は構造物の高さ |
| `hint` | 表示用の完成した日本語文 |

> **`bearing` は文章用、`azimuth` は作図用。** 8方位に丸めると最大22.5度ずれるので、
> 方位帯に印を置くときは必ず `azimuth` を使う。
> 例: 愛宕山は `bearing: "西"` でも `azimuth: 297.4` （西より27度北寄り）。

> **仰角は 2〜8度しかない。** 山は「低くて広い」ので、
> そのままの比率で描くとほぼ平らな線になる。**縦の誇張が要る**（docs/SPEC.md 2.6）。

### `kind` ごとの中身

| `kind` | `id` | `name` | 意味 |
|---|---|---|---|
| `point` | `tower` | 京都タワー | 人工物。可視データは PLATEAU 由来 |
| `peak` | `atago` / `daimonji` / `hiei` | 単独峰の名前 | **一点を指せる**ので精度が高い |
| `range` | `higashiyama` / `kitayama` | 東山 / 北山 | **連なり。**個別の山は名指ししない |
| `skyline` | `skyline` | 山の稜線 | `walk`（何m歩けば見えるか）, `directions` |
| `street` | `major_street` | その大通りの通り名 | 車の流れで気づく（下記） |

> **`range` は角幅が広い。**東山は洛中から見て 80度以上を占める。
> 「東山を正面に見て」という言い方は成り立たないので、文言も別にしている。
> 単独峰は `angular_width` が 10〜35度程度。

> `kind: "street"` は L4「大きい通り」（docs/SPEC.md 2.4）。
> `name` が固定文字列ではなく**実際の通り名**になる点に注意。
> このレイヤだけ PLATEAU の可視データを使わず、グリッド構造だけで確定する。
>
> 選ぶ基準は `major` フラグではなく **幅 15m 以上**、範囲は **600m 以内**。
> 「そこまで歩けば着く」ではなく「立った場所から車の流れで気づける」を意図している。

> **方位は実距離から計算する。** 添字の符号だけで判定すると、烏丸通の1本隣に
> 立っただけで 2.6km 先のタワーが「南西」になる（実際には真南に見えている）。
>
> **近すぎる目印は方位に使わない。** 京都タワーは131m。240m の地点では仰角29度、
> 120m では48度になり、見上げる形で水平方向が読みにくい。

### 3.3 `POST /api/arrival` — **フロント未使用**

> **答え合わせは v1 のスコープ外**（SPEC 2.3）。
> バックエンドには実装済みだが、画面からは呼ばれない。将来のために契約だけ残す。

到着した交差点を受け取り、目的地とのズレを講評する（SPEC 2.3）。

**リクエスト**

```json
{
  "target": { "ns": "ns-02", "ew": "ew-07" },
  "actual": { "ns": "ns-03", "ew": "ew-07" }
}
```

**レスポンス**

```json
{
  "correct": false,
  "off_by": { "ns": 1, "ew": 0 },
  "comment": "一本西入ってはりました。正解はC通どす。"
}
```

> v1 では後回しでよい。フロントは画面だけ用意して未接続でも可。

## 4. エラー

```json
{ "error": "INTERSECTION_NOT_FOUND", "message": "その交差点は存在しません" }
```

| コード | 発生条件 |
|---|---|
| `INTERSECTION_NOT_FOUND` | `exists` が false の交差点を指定された |
| `SAME_LOCATION` | `from` と `to` が同一 |
| `INVALID_STREET_ID` | 未知の street id |

## 5. 並行開発のための取り決め

### 5.1 モックデータ

`mock/grid.json` と `mock/route.json` に、**上記スキーマに完全準拠したサンプル**を置く。

- **フロントはバックエンドの完成を待たずに、このJSONを読んで開発する**
- バックエンドは、このJSONと同じ形を返すことをテストで保証する

### 5.2 仮のグリッドサイズ

| 軸 | 本数 | 仮の名前 |
|---|---|---|
| `ns`（縦） | 12 | `A通` 〜 `L通` |
| `ew`（横） | 16 | `1通` 〜 `16通` |

京都タワー: `ns-05` × `ew-15`（南端付近の中央）

> 実際の京都の通り名・本数は後から差し替える。
> **本数が変わっても壊れないコードを書くこと。**

### 5.3 契約変更の手順

1. このファイルを更新する
2. `mock/*.json` を更新する
3. 双方に共有する

**片方の都合で勝手に変えない。**
