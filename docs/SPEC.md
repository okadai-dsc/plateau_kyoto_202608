## 1. コンセプト

**Kyoter**（New Yorker ならぬ Kyoter）

> **地図を見ずに、目的地まで到達する。**

京都の住所システムそのものをナビゲーション言語として使う。緯度経度も地図も使わず、
「上ル×3、東入ル×2」だけで目的地にたどり着く体験をつくる。

### 成立させている2本の柱

#### ① 経路の表現 = 京都の住所文法

京都は碁盤の目状で、住所が「交差点名 + 方向」で表現される。

| 表記 | 方向 |
|---|---|
| 上ル（あがる） | 北 |
| 下ル（さがる） | 南 |
| 東入ル（ひがしいる） | 東 |
| 西入ル（にしいる） | 西 |

これを使うと、経路を `上ル×3 → 東入ル×2` と表現できる。**京都でだけ成立する経路記法。**

#### ② 方位の取得 = 京都タワー

①は「自分が今どちらを向いているか」が分からないと使えない。
そこでコンパスの代わりに**京都タワー**を使う。

京都タワーは烏丸通上・京都駅北、つまり洛中のほぼ南端にある。
→ **タワーが見える方向 ≒ 南** → 上下東西がすべて確定する。

#### ③ PLATEAU の役割 = ②が成立する場所の事前計算

タワーは常に見えるわけではない（建物で遮蔽される）。
そこで PLATEAU の建物モデルから **逆可視領域（reverse viewshed）** を事前計算する。

- 視点 = 京都タワー頂部（塔頂 131m / 展望室 GL+100m）
- 対象 = 歩行者目線 1.5m
- 出力 = 地点ごとに `{可視/不可視, 方位角, 仰角, 見え方（全体/上部のみ）}`

これを経路探索に組み込むことで **「方位を見失わない経路」を選べる**。
ここが本企画の技術的な核。

## 2. 設計上の発見

### 2.1 命令文はランドマーク基準の回転で書ける

方位（北/南/東/西）を直接言う必要はない。

> 「京都タワーを**背にして**、3本上ル。**右手**に2本入ル。」

ユーザーは方位を知る必要すらない。これが最も Kyoter らしい文法。

### 2.2 GPS は「使う / 使わない」ではなく「いつ使うか」

| フェーズ | GPS | 方針 |
|---|---|---|
| スタート時 | **使う** | 初期位置の確定。ただし地図は出さず「現在地：四条烏丸」とテキストのみ |
| 道中 | **使わない** | ここがコンセプト。追従した瞬間ただのナビになる |
| ゴール時 | **使う** | 答え合わせ |

京都では交差点名がそのまま住所なので、本来は手入力（南北通り × 東西通り を選択）が最も自然。
ただし初回の観光客にはハードルが高いため、
**GPSで「今ここですね？」と候補提示 → ユーザーが確認** を主動線とし、手入力も残す。

### 2.3 到達判定は「合否」ではなく「講評」

体験の山場は着いた瞬間ではなく、
**着いたか分からないまま歩いて「合ってた！」となる瞬間**。判定がないとオチがない。

ただし ✗ を突きつける設計は苦しいので、**ズレを京都語で講評する**。

> 「一本西入ってはりました」
> 「烏丸通で止まらはったけど、正解は室町通どす」

ズレても面白い状態にする。スコアは「ズレ本数 / 所要時間 / ギブアップ有無」程度で十分。

**ギブアップボタン（＝地図が出る＝負け）** を置くと道中に緊張感が生まれる。体験装置として効く。

### 2.4 ランドマークはレイヤ化する

京都タワーが見えないときは他のランドマークで代用する。
山は遠く建物に遮られにくいため、**可視領域がタワーより圧倒的に広い**と見込まれる。

| レイヤ | ランドマーク | 特性 | 与える方位 |
|---|---|---|---|
| **L1** | 京都タワー | 点・高精度・可視域は狭い見込み | 南 |
| **L2** | 大文字（如意ヶ嶽）/ 比叡山 / 東寺五重塔 | 点として使える・可視域広い | 東〜北東 / 北東 / 南西 |
| **L3** | 東山連峰の稜線 | 面・低精度だがほぼ全域から見える | 東 |

地点ごとに「使える最上位のランドマーク」を提示する。
**山の可視判定には PLATEAU の地形データ(dem) が必須。**

## 3. スコープ

### 3.1 成果物

**Web アプリ**

### 3.2 対象エリア

通り名住所が成立するのは洛中。

- 北: 北大路通
- 南: 十条通（京都タワー / 京都駅を含める）
- 東: 東大路通（以東は東山で碁盤が崩れる）
- 西: 西大路通

約 30km²。

**方針: 計算対象は洛中全域とし、v1の提供エリアは可視領域の計算結果を見てから絞る。**
エリアを先に確定すると、計算結果次第で手戻りする。

### 3.3 対象外

嵐山・伏見・山科など、通り名住所の文法が破綻する地域。

## 4. データ

### 4.1 PLATEAU 京都市

[G空間情報センター](https://www.geospatial.jp/ckan/dataset/plateau-26100-kyoto-shi-2025) にて 2022〜2025年度が公開済み。

| 項目 | 内容 |
|---|---|
| 最新 | 2025年度 |
| 建築物 | LOD0 / 1 / 2.0 / 3.3 |
| 整備範囲 | LOD1: 185.0km² / LOD2: 24.24km² |
| 形式 | CityGML, 3DTiles |
| その他 | 地形(dem)、道路(tran)、都市計画、土地利用、災害リスク、都市設備、植生、橋梁 |

### 4.2 必要なデータ

- **bldg**（建築物）— 遮蔽判定
- **dem**（地形）— 山ランドマークの可視判定に必須
- **tran**（道路）— 通りグラフの生成
- 通り名データ — PLATEAU tran に通り名属性があるか要確認。無ければ OSM を検討

## 5. 決定事項まとめ

| # | 論点 | 決定 |
|---|---|---|
| 1 | 「×3」の単位 | **通り名ベース + 本数併記**（`3本上ル ＝ 丸太町通`）。京都は通り名標識が優秀なので、ユーザー自身がズレを検出・復帰できる。純カウントは1本ミスると詰む |
| 2 | GPS | **フェーズで切り分け**（2.2参照）。道中は使わない |
| 3 | タワーが見えない時 | **他ランドマークで代用**。レイヤ化して提示（2.4参照） |
| 4 | 対象エリア | **計算は洛中全域、提供範囲は可視領域の結果を見て決定**（未確定） |
| 5 | 成果物 | **Web アプリ** |
| 6 | 到達判定 | **実装する。合否ではなく京都語での講評**（2.3参照） |

## 8. 次の一手

**可視領域の計算を最小構成で1回まわす。**

論点4（提供エリア）と、そもそもの企画の実現形がこれで決まるため、最優先の技術検証とする。

- 京都タワー頂点 → 洛中の道路中心線上サンプル点への遮蔽判定のみ
- 出したい数字: **洛中の何%の道路から京都タワーが見えるか**

この結果次第で、
- 広ければ → タワー単独でコンセプトが成立
- 狭ければ → ランドマーク群（L2/L3）前提の設計に切り替え

が決まる。
