# Kyoter — 仕様書（ドラフト）

> 状態: 議論メモ。決定事項と未決事項を区別して記載。
> 最終更新: 2026-08-08

## 1. コンセプト

**Kyoter**（New Yorker ならぬ Kyoter）

> **地図を見ずに、目的地まで到達する。**

京都の住所システムそのものをナビゲーション言語として使う。緯度経度も地図も使わず、
「上ル×3、東入ル×2」だけで目的地にたどり着く体験をつくる。

### 成立させている2本の柱

#### ① 経路の表現 = 京都の住所文法

京都は碁盤の目状で、住所が「交差点名 + 方向」で表現される。

| 表記 | 方向 |
|---|---|
| 上ル（あがる） | 北 |
| 下ル（さがる） | 南 |
| 東入ル（ひがしいる） | 東 |
| 西入ル（にしいる） | 西 |

これを使うと、経路を `上ル×3 → 東入ル×2` と表現できる。**京都でだけ成立する経路記法。**

#### ② 方位の取得 = 京都タワー

①は「自分が今どちらを向いているか」が分からないと使えない。
そこでコンパスの代わりに**京都タワー**を使う。

京都タワーは烏丸通上・京都駅北、つまり洛中のほぼ南端にある。
→ **タワーが見える方向 ≒ 南** → 上下東西がすべて確定する。

#### ③ PLATEAU の役割 = ②が成立する場所の事前計算

タワーは常に見えるわけではない（建物で遮蔽される）。
そこで PLATEAU の建物モデルから **逆可視領域（reverse viewshed）** を事前計算する。

- 視点 = 京都タワー頂部（塔頂 131m / 展望室 GL+100m）
- 対象 = 歩行者目線 1.5m
- 出力 = 地点ごとに `{可視/不可視, 方位角, 仰角, 見え方（全体/上部のみ）}`

これを経路探索に組み込むことで **「方位を見失わない経路」を選べる**。
ここが本企画の技術的な核。

## 2. 設計上の発見

### 2.1 命令文はランドマーク基準の回転で書ける

方位（北/南/東/西）を直接言う必要はない。

> 「京都タワーを**背にして**、3本上ル。**右手**に2本入ル。」

ユーザーは方位を知る必要すらない。これが最も Kyoter らしい文法。

### 2.2 GPS は使わない

**v1 では全フェーズで GPS を使わない。**

| フェーズ | 方針 |
|---|---|
| スタート時 | ユーザーが**交差点まで移動して、その場所を選択式で入力**（4.7） |
| 道中 | 使わない。追従した瞬間ただのナビになる |
| ゴール時 | 到着した交差点を同じ選択式で入力 → 目標との差分を講評（2.3） |

京都では交差点名がそのまま住所なので、手入力が最も自然。
現地の通り名標識を読めば自分の位置が分かる ── **この「標識を読む」動作自体が体験の一部**。

> **結果として v1 は緯度経度を一切使わない。** GPS を将来乗せる場合は 4.6 を参照。

### 2.3 到達判定 — **v1 スコープ外**

> **やらない。** 歩行中の「着いた」で最初の画面に戻るだけ。
> バックエンドに `POST /api/arrival` は実装済みだが、画面からは呼ばない。
>
> 以下は将来やる場合の設計として残す。

#### （参考）到達判定は「合否」ではなく「演出」

体験の山場は着いた瞬間ではなく、
**着いたか分からないまま歩いて「合ってた！」となる瞬間**。

ただし本企画はゲームではなく観光の移動手段（3.1参照）なので、スコアで競わせない。
ズレは ✗ ではなく**京都語で講評する**。

> 「一本西入ってはりました」
> 「烏丸通で止まらはったけど、正解は室町通どす」

**ギブアップボタン（＝地図を見る＝観光客に戻る）** がコンセプト上の敗北条件になる。

**判定に GPS は要らない。** 到着した交差点を 4.7 と同じ選択式で入力してもらえば、
目標との差分がそのまま出る。座標ゼロのまま体験が最後まで閉じる。

> **優先度: 低。** コアではなく演出。v1では後回しでよい。

### 2.4 ランドマークはレイヤ化する

京都タワーが見えないときは他のランドマークで代用する。

> 当初は「山は遠く建物に遮られにくいので、可視領域はタワーより圧倒的に広い」と
> 見込んでいた。**実測すると逆だった**（後述）。

**すべて PLATEAU（建物・地形）+ 国土地理院（遠方の地形）で実測した値。**

| レイヤ | ランドマーク | 種別 | 高さ | 実測カバー率 |
|---|---|---|---|---|
| **L1** | 京都タワー | 人工物 | 131m | **44 (9%)** |
| **L2** | 愛宕山 | 単独峰 | 924m | **14 (3%)** |
| **L3** | 大文字（火床） | 単独峰 | 330m | **7 (1%)** |
| **L4** | **東山** | **連なり** | 実地形 | **51 (11%)** |
| **L5** | 北山 | 連なり | 実地形 | **24 (5%)** |
| **L6** | 比叡山 | 単独峰 | 848m | **0 (0%)** |
| **L7** | 山の稜線（方角と歩く距離） | | | **127 (27%)** |
| **L8** | **大きい通り** | 車の流れ | | **212 (44%)** |

（各行は「そのレイヤで初めて手がかりが得られる交差点」の数。実在479交差点）

> ### 山はほとんど見えない
>
> **山と塔で方角が分かるのは 140 / 479（29%）だけ。** 残りの71%は
> 稜線（歩けば見える方角）か、大きい通り（車の流れ）に頼ることになる。
>
> **つまり実質の主役は L8「大きい通り」（44%）である。**
> このレイヤだけ PLATEAU を使わない（通りの幅と実在マスクだけで決まる）。

#### 推定は実測と桁違いだった

PLATEAU を入れる前、「軸から30°以内・400m以上見通せれば見える」という規則で
推定していた。実測すると合っていなかった。

| 山 | 推定 | **実測** |
|---|---|---|
| **愛宕山** | 317 (66%) | **14 (3%)** |
| 大文字 | 37 (8%) | 7 (1%) |
| **比叡山** | 0 (0%) | **15 (3%)** |

**愛宕山は22分の1。** 「400m抜けていれば見える」としていたが、実際には通りの先に
建物が連続していて、どこか1棟でも高ければ視線は切れる。
また「比叡山は北東で通りの軸に乗らないから最下位」という線引きにも根拠がなく、
実測では愛宕山と同程度だった。

> 参考にした[街中から見える山々](http://www.toshiomi.net/kyotojtn/matiyama.htm)の
> 「愛宕山は街中ならどこからでも西側に高く見える」は、
> **通りに立った歩行者目線では成立しない**。同ページの写真が金戒光明寺の鐘楼や
> 橋の上から撮られているのは、高い場所や開けた場所が要るからだと考えられる。

#### 優先順位は「同定しやすさ」順

**単独峰 > 連なり**。単独峰は一点を指せるが、連なりは方角しか教えてくれない。

| 目印 | 同定できるか |
|---|---|
| 京都タワー | ✓ 人工物・唯一無二 |
| 愛宕山 | ✓ 単独峰・西で一番高い |
| 大文字 | ✓ 火床の「大」がある |
| **東山 / 北山** | **✗ 連なりの中の個別の山は見分けられない** |

だから **連なりでは個別の山を名指ししない**。
「北山（天ヶ岳）が北に見えます」は、17.9km先・仰角2.4°で天ヶ岳という
一峰を見分けろと言っているに等しく、ユーザーが検証しようがない。

```
不可: 北山（天ヶ岳）が北に見えます。北山（天ヶ岳）の方が上ルです。
可:   北に北山の山並みが広がっています。そちらが上ルです。
```

#### 連なりは点では表現できない

東山は洛中から見て**水平方向に80度以上**（比叡山〜稲荷山）を占める。
地平線の4分の1が東山になるので、一点では表現できない。

そこで東山・北山は `ends`（尾根の両端）で持ち、可視判定では
**尾根に21点置いて、どの点が見えたかを記録する**。

> **描くのは尾根全体ではなく、見えている部分だけ。**
> 実測では建物の切れ目から覗く範囲になり、東山でも角幅の中央値は 8.7°、最大 48.3°。
> 「東山が80度に広がって見える」わけではない。

> **この項は実地の指摘から見つかった。**当初モデルには東山が無く、
> 千本通×七条通で「北山が北に見える」と出していた。七条通は東へ真っ直ぐ
> 東山に突き当たるので、東に山が見えるという指摘を受けて連なりを追加した。
> なお実測ではこの交差点の最上位の手がかりは稜線（北東）になっている。

#### 格子は 5m では足りない ── 1m に上げた

当初 5m 四方の格子で計算していたが、**幅4〜5mの通りが両側の建物で埋まり、
見通しが消えていた**。堺町通のストリートビューで、実際には数百m先まで
抜けていることを確認して判明した。

建物の高さ自体は合っていた（南20m先に6.6m＝2階建ての町家）。
問題は位置で、6.6mの建物が20m先にあると仰角14.2°になり、3〜5°の山を全部隠す。

そこで**近くは1m・遠くは5m**の2段構えにした。

| 層 | 格子 | 範囲 |
|---|---|---|
| 建物 | **1m** | 洛中＋1km（5100万セル） |
| 地形 | 5m | 全域25km |

視線をたどる刻みも、近く400mは1m・以降5mにした。

| 目印 | 5m格子 | **1m格子** |
|---|---|---|
| 京都タワー | 44 (9%) | **88 (18%)** |
| 愛宕山 | 14 (3%) | **29 (6%)** |
| 大文字 | 17 (4%) | **38 (8%)** |
| **東山** | 86 (18%) | **232 (48%)** |
| **北山** | 53 (11%) | **200 (42%)** |
| 比叡山 | 15 (3%) | **31 (6%)** |

**軒並み2〜4倍。** 格子の粗さが結論を変えていた。

#### 可視判定は PLATEAU の実測

`visible.json` に PLATEAU + 国土地理院で計算した結果が入っている
（`tools/calc_viewshed.py`）。

- 地形(dem)と建物(bldg)を **5m四方の地表面グリッド**に焼く
- 各交差点の**目線1.5m**から目印の頂部へ視線を引き、遮られていないか調べる
- 連なりは尾根に21点置き、**どの点が見えたか**を記録する
  → 描画では「実際に見えている部分」だけを角幅にできる

> **PLATEAU の地形は愛宕山・比叡山に届かない。**
> dem の西端は135.650、愛宕山は135.632。東端は135.825、比叡山は135.833。
> 1km前後足りないため、遠方の地形だけ**国土地理院の標高タイル（10mメッシュ）**で
> 補っている（`tools/fetch_gsi_dem.py`）。**建物は PLATEAU にしか無い。**


#### なぜ「山は建物の上に出る」という読みが外れたか

推定の根拠にしていた仰角の比較は、数字そのものは正しい。

| 対象 | 仰角（概算） |
|---|---|
| 愛宕山（13km・924m） | 約3.8° |
| 比叡山（10km・848m） | 約4.5° |
| 大文字（5km・465m） | 約4.9° |
| 31mのビル 500m先 | 3.5° |
| 15mのビル 500m先 | 1.7° |

外したのは**「通りの先のビルは1棟」と暗に仮定していた**点。
実際には視線上に建物が何百棟も並び、**そのどれか1棟でも高ければ切れる**。
1棟ずつの勝ち負けではなく、連続した障害物の最大値との勝負だった。

これは机上の仰角比較では出てこず、**PLATEAU の建物モデルを通して初めて分かった**。
本企画で PLATEAU が効いているのは、まさにここ。


#### L4「大きい通り」— 最後の手がかり

L1〜L3 が見えないときに使う。狙いは、通り名の標識を読ませることでも、
そこまで歩かせることでもない。

> **立った場所から「あっちは車がよく通ってるな」と気づかせる。**

突き当たりを横切る車、空の開け方、車の音。地元の人が無意識にやっている判断を、
そのまま指示文にする。

```
北の方を車がよく通っています。あちらが御池通です。御池通の方が上ルです。
西の方を車がよく通っています。あちらが堀川通です。堀川通を正面に見て、右手が上ルです。
```

##### 選ぶ基準は `major` ではなく「幅」

`major` は「通り抜ける主要な通り」の意味であって、車が通るかどうかとは別物。

| 通り | 幅 | `major` | 車の流れ |
|---|---|---|---|
| 寺町通 | 8m | ✓ | アーケードの商店街。ほぼ通らない |
| 三条通 | 8m | ✓ | 細い通り。ほぼ通らない |
| 御池通 | 50m | ✓ | ✓ |
| 堀川通 | 50m | ✓ | ✓ |

そこで **幅 15m 以上**（2車線＋歩道）を「車がよく通る大通り」とする。
気づける範囲として **600m 以内**に限る。

| 幅の閾値 | 400m以内 | 600m以内 | 800m以内 |
|---|---|---|---|
| ≥12m | 97.1% | 99.6% | 100% |
| **≥15m** | 96.7% | **98.7%** | 100% |
| ≥22m | 93.3% | 94.4% | 98.5% |

> `major` は使わなくなったわけではない。**通りが分断されていないかの検査**には
> 引き続き使う（大通りは必ず通り抜けるので、そこが欠けていれば本当に切れている）。

**このレイヤだけ PLATEAU が要らない。**
通りに沿った視線は通りそのものが視線経路なので、建物は遮らない。
見通せるかどうかは「その通りが途中で切れていないか」だけで決まり、
それは交差点の実在マスク（4.5.2）が既に持っている。
つまり **L4 は現在の実装がそのまま最終形**になる。

> 見通し判定は **大きい通りとの交点だけ**を検査する。
> 交点が無いのは「細い通りがそこまで届いていない」という意味であって、
> 見通す側が分断されているとは限らないため。大通りは必ず通り抜けているので、
> そこが欠けていれば本当に切れている（御所・二条城など）と判定できる。

##### 「街区の形」から差し替えた経緯

当初 L4 は「街区の形」（次の交差点までの距離が南北と東西で違う）だった。
しかしこれは**南北軸か東西軸かを言うだけで、北か南かは分からない**。

実データで測ったところ、この差が致命的だった。

| | 街区の形 | 大きい通り |
|---|---|---|
| L4 に落ちる交差点 | 224 / 479 (46.8%) | 224 / 479 (46.8%) |
| **方角が出ない交差点** | **227 (47.4%)** | **3 (0.6%)** |

実在交差点の半分近くで方角が出ていなかった。差し替えでこれが解消した。
（残る3件は京都タワーの足元 = 塩小路通で、200m以内は見上げる形になるため意図的に方位を出さない）

地点ごとに「使える最上位のランドマーク」を提示する。

### 2.5 PLATEAU の使いどころ

山の座標・標高は**ネット情報（Wikipedia / 地理院地図 / OSM）で足りる**。
PLATEAU に山の名前は入っていない（地物の形状モデルであって地名データではない）。

では PLATEAU は何に要るのか。**「本当に見えるか」と「どう見えるか」**である。

| やりたいこと | 必要なデータ |
|---|---|
| 山の方位を出す | ネット情報の座標だけで足りる（実装済み） |
| **本当に見えるか** | **bldg (LOD1)** — 建物による遮蔽 |
| **どう見えるか（シルエット）** | **dem + bldg** — 地平線プロファイル |

#### 地平線プロファイル

建物と地形を**1枚の標高面(DSM)にまとめ**、視点（目線1.5m）から方位ごとにレイを飛ばして
仰角の最大値を拾う。

```
方位:   ...  75°   76°   77°   78°   79°   80° ...
仰角:   ... 14.2  14.2   3.8   3.9   3.8  15.1 ...
正体:   ... bldg  bldg  山    山    山   bldg ...
                        ^^^^^^^^^^^^^^^  ビルの切れ目から山が覗いている
```

これが出れば **L1〜L6 の可視判定はすべてここから読める**。

| 判定したいこと | プロファイルからの読み方 |
|---|---|
| 京都タワーが見えるか | タワーの方位での仰角がプロファイルより高いか |
| 山が見えるか | 同上 |
| 稜線が見えるか | `src == terrain` の方位があるか |
| シルエット表示 | プロファイルそのもの |

- データ量: 479交差点 × 360方位 → **1MB程度**。フロントに丸ごと渡せる
- 最適化: 建物は近傍のみ（30mのビルは1km先で1.7°）、地形は遠方まで
- 限界: LOD1は箱モデルなので屋根形状は出ない。街路樹・電線は入らない
- **要確認:** demは二次メッシュ（約10km四方）単位配布。愛宕山13km・比叡山10kmが
  含まれるかはデータを落として確認する。足りなければ
  国土地理院の基盤地図情報10mメッシュ標高（DEM10B・全国・無償）で補う

### 2.6 山は「低くて広い」

四条烏丸から見た実測値。

| 山 | 方位 | 距離 | **仰角** | **見かけの幅**（山塊3km仮定） |
|---|---|---|---|---|
| 愛宕山 | 299° | 13.4km | **3.7°** | **12.8°** |
| 比叡山 | 41° | 10.1km | **4.5°** | **16.9°** |
| 大文字 | 56° | 4.6km | **5.1°** | **35.8°** |
| 北山（天ヶ岳） | 360° | 16.2km | **2.6°** | **10.6°** |

**縦横比が 1:3 〜 1:7。** そのままの比率で描くと画面上ではほぼ平らな線になるので、
**縦を3〜5倍に誇張する**必要がある。これは描画方式（A/B/C）によらない制約。

#### 描画の3段階

| 段階 | 中身 | 必要なデータ | 状態 |
|---|---|---|---|
| **A. マーカー** | 方位と仰角に印を置く | 座標＋標高 | 完了 |
| **B. 模式シルエット** | 角幅を持たせ、単独峰は三角・連なりは台形 | ＋山塊の幅 / 連なりの両端 | 完了 |
| **C. 実景の線画** | **建物を透視投影した線画＋実際の稜線** | **dem + bldg** | **完了** |

### C ── 採用した形

**方位帯（A/B）はやめて、その場に立って目印の方を見た景色を線画で描く。**

PLATEAU の LOD1 は建物を箱として持っているので、目線1.5mから透視投影すれば
そのまま絵になる。両側の建物が奥へ狭まり、突き当たりに山が出る ──
ストリートビューと同じ構図。**色は付けない。**

- 隠面は画家のアルゴリズム（遠い面から白く塗って線を描く）
- 山の稜線は地平線プロファイルの仰角を同じカメラに乗せる
- 誇張なし。視野 横72°

#### なぜ方位帯では駄目だったか

「東に山が見えます」だけでは、**三方が山の京都では絞れない**。
見回すと複数の方角に山があり、どれが東かユーザーには分からない。

**形を見せれば一致させられる。** 方角の曖昧さを、輪郭の一致で解く。

#### 事前生成する

1視点445枚の面・59KB。479視点で約27MB。リクエスト時に描くと遅いので、
`tools/gen_scenes.py` で全交差点ぶんを事前に SVG にする。

| 削減の手 | 面の数 |
|---|---|
| そのまま（半径320m） | 3,800 |
| 足元の面を捨てる | 2,600 |
| 半径180m・小さい面を捨てる | 854 |
| 裏を向いた壁を捨てる | **445** |

**Bは見た目の改善ではなくデータモデルの修正だった。**
連なり（東山・北山）は角幅を持たなければ表現できず、点として扱っていたことが
「東山が抜けている」というバグの原因だった。

Bでも作れないのは **尾根の繋がり・山どうしの重なり・建物による切り取り** の3つ。
「スマホをかざして実景と重ねる」体験はCでしか成立しない。

#### 作図には `azimuth` を使う

8方位に丸めると最大22.5度ずれる。文章は `bearing`、作図は `azimuth`（度）と使い分ける。

> 例: 愛宕山は `bearing: "西"` だが `azimuth: 297.4`。**実際は西より27度北寄り。**
> 愛宕山は盆地の北西寄りにあるため、洛中中心からは「北西」に見える。
> 参考ページの「西側に高く見える」という記述は大づかみだった。

## 3.5 経路生成：グラフ探索は不要

碁盤の目なので、**通りの並び順の差分を取るだけ**で経路が決まる。
A* 等のグラフ探索は要らない。

```
現在地: 四条 × 烏丸     目的地: 三条 × 河原町
南北: 四条 → 三条  = N本 上ル
東西: 烏丸 → 河原町 = M本 東入ル
```

### 経路は指定しない ← 企画の核

「上ル」と「東入ル」は**どの順に消化しても着く**。
だから伝えるのは **方角2つと本数2つ** だけでよい。

```
上ル    三条通まで   およそ4本
西入ル  烏丸通まで   およそ11本
        順番は自由
```

**覚えやすさがこの企画の価値**であり、順番まで決めると普通のナビになって消える。
経路候補を出したり、手順①②と並べたりしない。

> **本数は目安、通り名が正。**
> 実際に横切る本数は通る道で変わる（河原町通を四条から三条へ上がると1本、
> 寺町通なら4本。錦小路・蛸薬師・六角が河原町通まで届かないため）。
> 順番が自由である以上ひとつに定まらないので、通り名で答え合わせできるようにする。

### 目印の役割

目印は経路を選ぶためではなく、**どちらが上ルかを知るため**にある。

> 「大文字が北東に見えます。大文字を正面に見て、左前が上ルです。」

方位を意識しなくても、目印ひとつで四方向が決まる。

#### 目印は複数ある（レイヤ化・2.4）

京都タワーだけでは足りない。**洛中の交差点の11%からしか見えない**（仮データ）。
そこで山を加える。山は遠くて大きいので建物に遮られにくく、可視範囲が桁違いに広い。

| レイヤ | 目印 | 使える交差点（実在479のうち） |
|---|---|---|
| L1 / L2 | 京都タワー・大文字 | 50 (10.4%) |
| L3 | 山の稜線 | 205 (42.8%) |
| L4 | **大きい通り** | **224 (46.8%)** |
| | **方角が出ない** | **3 (0.6%)** |

見える中でいちばん精度の高いものを選ぶ。L1〜L3 の可視判定には **PLATEAU** が要る
（山は地形データ(dem)も要るので建物(bldg)だけでは計算できない）が、
**L4 だけは PLATEAU なしで確定する**（2.4）。

#### 方位は実距離から出す

添字の符号だけで判定すると、烏丸通の1本隣に立っただけで 2.6km 先のタワーが
「南西」になってしまう（実際には真南）。通りの `pos`（m）から角度を計算して8方位に丸める。

#### 近すぎる目印は使わない

京都タワーは131m。240m の地点で仰角29度、120m で48度になり、
見上げる形になって水平方向が読みにくい。一定距離より近い目印は方位を返さない。

### 例外処理

御所・二条城・寺社・市場など **通り抜けできない街区** がある。
これも座標ではなく「この区間は通れない」という**禁止区間リスト**で表現できる。

## 4.5 目的地の指定方法

**碁盤の目を模したブロック状の地図（グリッドUI）で指定する。**

- 実際の地図（航空写真・道路図）ではなく、**通り名が並んだ抽象的な格子**を表示する
- ユーザーはその格子上のブロックを選ぶ
- 地理的な地図を見せないため、コンセプト（地図を見ずに）と矛盾しない

**描画に座標は不要。** 4.3 の通り順テーブルだけで N×M の格子が引ける。

### 4.5.1 内部表現は「交差点」で固定する

UIがブロック（街区）選択でも交点選択でも、内部では交差点として保持する。

```python
Destination = { "ns": "烏丸通", "ew": "四条通" }
```

京都の住所（交差点 + 方向）と同じ構造なので、指示文生成にそのまま渡せる。
UIの選択単位が後から変わっても内部モデルを変更せずに済む。

### 4.5.2 実在マスクが必要

通りによっては全区間を走っていない（例: 錦小路は堀川以西に存在しない）。
格子には**その交差点が実在するかの真偽値マスク**が要る。

座標は不要（N×M の bool 行列）だが、**実データの調査が必要**。

### 4.5.3 Google の URL から取り込む — **スコープ外（保留）**

> **v1 では実装しない。** 目的地の指定はグリッドUI（4.5）に一本化する。

将来やる場合の想定だけ残しておく。

1. 短縮URL（`maps.app.goo.gl/...`）を展開する
2. 緯度経度を取り出す
   - URL から直接抽出（`@34.xxx,135.xxx` や `!3d` / `!4d`）
   - または Google Places API（APIキーと課金枠が必要だが堅い）
3. **緯度経度 → 交差点** に変換する（4.6）

保留の理由と注意点:

- Google が返す京都の住所は「中京区中之町565」のような**町名表記**で、
  「四条烏丸上ル」ではない。**通り名は直接もらえない**ため必ず 4.6 の座標変換を経由する
- ユーザーが共有ボタンでコピーすると短縮URLになるので、リダイレクト追跡が要る
- **この機能だけが「座標なし」の原則を破る**

### 4.5.4 副入力：観光地から選ぶ — **実装済み**

観光客が行きたいのは「三条 × 河原町」ではなく「錦市場」。
通り名を知らなくても目的地を選べる入口を用意する。

京都の店・施設の住所はもともと通り名表記なので、変換が自明。

```
錦市場 → 錦小路通 × 寺町通
東寺   → 九条通 × 大宮通
```

グリッド上では次のように示す。

| 表現 | 内容 |
|---|---|
| チップ | グリッドの上に観光地名を並べる。押すと目的地になる |
| 印（◉） | 代表する交差点に置く |
| 淡い塗り | 敷地の広がり（京都御苑・二条城・京都駅・錦市場など） |

データは `tools/kyoto_streets.json` の `spots`、契約は [API.md](API.md) 3.1 の `spots`。

## 4.6 緯度経度 → 交差点の変換

京都の碁盤の目は**ほぼ真北を向いている**ため、以下だけで変換できる。

- 南北の通り → **経度**の配列（通り1本につき数値1個）
- 東西の通り → **緯度**の配列（通り1本につき数値1個）

緯度経度が来たら、2つの配列を二分探索で挟み込むだけで交差点が決まる。
通りが50本ずつでも数値は100個。**全面的なジオコーダは要らない。**

```python
ns_lon = {"寺町通": 135.7692, "烏丸通": 135.7595, ...}
ew_lat = {"三条通":  35.0090, "四条通":  35.0036, ...}
```

> **v1 では使わない。** GPS を将来乗せる段階で初めて必要になる。

### この仕組みが効く場面

| 用途 | 入力 | 参照 | v1 |
|---|---|---|---|
| GPSでの初期位置取得 | 端末のGPS | 2.2 | **不使用**（選択式入力で代替） |
| ゴール時の答え合わせ | 端末のGPS | 2.3 | **不使用**（選択式入力で代替） |
| Google URLからの目的地取り込み | URLから抽出した座標 | 4.5.3 | **スコープ外** |

**この配列は仮データで進められる。** 正確な値は後から差し替えるだけでよい。

### v1 は座標ゼロで完結する

**座標を使う機能が v1 から全て消えた。**

| 場面 | v1 の方式 | 座標 |
|---|---|---|
| 目的地の指定 | グリッドUIで選択（4.5） | 不要 |
| 現在地の指定 | 交差点まで移動 → 選択式で入力（4.7） | 不要 |
| ゴール判定 | 到着した交差点を選択式で入力（2.3） | 不要 |

つまり 4.6 は v1 の必須要素ではなく、**GPS を乗せる段階で初めて要る**。
**バックエンドは完全に座標なしで書き切れる。**

## 4.7 現在地の指定方法

**ユーザーが交差点まで移動し、その交差点を選択式で入力する。**

GPS は使わない。現地の通り名標識を読んで自分の位置を知る ──
**この動作自体が「観光客っぽくない振る舞い」の一部**になる。

### 4.7.1 入力UI：縦と横をそれぞれ選ぶ

英語圏の `5th Ave × 42nd St` と同じ構造。**2つのセレクタで交差点を指定する。**

```
[ 南北の通り ▼ ]  ×  [ 東西の通り ▼ ]
    烏丸通              四条通
```

- 自由入力ではなく**選択式**（表記ゆれ・誤字が発生しない）
- 交差点は必ず「南北 × 東西」の組なので、2つ選べば一意に決まる

> **New Yorker が通り名で位置を言うのと同じ構造を京都でやる。**
> Kyoter という名前の根拠が、入力UIのレベルでも成立している。

### 4.7.2 選択肢の並び順は通り順にする

50音順ではなく **4.3 の通り順（数え歌の順）** で並べる。

- 実際の街の並びと一致するので探しやすい
- 使っているうちに通りの順番が頭に入る（＝京都人に近づく）

### 4.7.3 実在しない組み合わせは選ばせない

片方を選んだ時点で、もう片方を**実際に交差する通りだけに絞り込む**。
4.5.2 の実在マスクをここで使う。

### 4.7.4 同じUIを3箇所で使い回す

| 場面 | 用途 |
|---|---|
| スタート時 | 現在地の入力 |
| ゴール時 | 到着した交差点の入力 → 差分を講評（2.3） |
| 目的地（副） | グリッドUI（4.5）の代替入力 |

**したがって PLATEAU からの可視領域計算は本作業のスコープ外。**

### 4.8.1 道路ネットワークデータ

- 対象地域の道路ネットワーク
- **通り名が付与されている**

| 用途 | 参照 |
|---|---|
| 通り順テーブルの検証 | 4.3 |
| 交差点の実在マスクの生成 | 4.5.2 / 4.7.3 |
| 通り抜けできない街区の把握 | 3.5 |

### 4.8.2 交差点ポイントデータ

- 交差点のポイントデータ
- **京都タワーが見える / 見えない の属性が付与されている**

これで 1章③ の逆可視領域計算が不要になる。**PLATEAU の処理は提供側が担当。**

### 4.8.3 これで確定すること・しないこと

**確定する:**

- 各交差点でタワーが見えるか（L1）
- 経路選択に「見える交差点を通る」を組み込める（3.5）

**含まれないので設計を変えるもの:**

| 項目 | 元の想定 | 対応 |
|---|---|---|
| タワーの方位 | データに含める想定だった | **グリッドから計算できる**（下記）ので不要 |
| L2 / L3 ランドマーク | 大文字・比叡山・東山稜線（2.4） | **v1では扱わない。L1のみ** |

#### タワーの方位はデータ不要

京都タワーの位置は **烏丸通 × 塩小路通** で固定。
現在地も通り名で分かっているので、**通り順配列の添字を比べるだけで方位が出る。**

```
現在地: 四条通 × 河原町通
タワー: 塩小路通 × 烏丸通
  塩小路は四条より南  → タワーは南
  烏丸は河原町より西  → タワーは西
  ⇒ 南西
```

8方位あれば「タワーを背にして」「右手に見て」には十分。
**座標も可視データも要らない。**

### 4.8.4 データ形式への要望

**交差点ポイントデータに、交差する2本の通り名を入れてほしい。**

```
ns_street:     "烏丸通"
ew_street:     "四条通"
tower_visible: true
```

通り名で持ってもらえれば、こちらの通り順テーブルと**座標を介さず直接結合できる**。
座標だけだと 4.6 の変換が必要になり、v1の「座標ゼロ」（4.6末尾）が崩れる。

> **未確認:** 実際のフォーマット（GeoJSON / CSV / Shapefile 等）、
> 「見える / 見えない」の中間値（部分的に見える等）の有無。

## 8. 次の一手

**可視領域の計算は本作業のスコープ外**（4.8で外部から受け取る）。
したがってバックエンド実装に一本化できる。

### 座標なしで作るバックエンド（今すぐ着手可能）

1. 通り順テーブル（数え歌を配列化）
2. 住所パーサ
3. 経路の分解 → 複数パターン列挙
4. 指示文の生成（タワー方位はグリッドから算出：4.8.3）
5. 目的地マスタ（スポット20件）
6. 現在地入力の2セレクタ用データ（4.7）

可視性は 4.8 のスキーマに合わせた**仮データ**で埋めておき、
本物が届いたらファイルを差し替えるだけにする。

### 受領後にやること

1. 仮データを本物に差し替える
2. 通り順テーブルを道路ネットワークデータと突き合わせて検証
3. 実在マスクを道路ネットワークから生成（4.5.2 / 4.7.3）
4. **タワーが見える交差点の割合を集計** → 提供エリアの確定（3.3）
