# Kyoter — フロントエンド仕様

> 担当者向け作業指示書。
> **必読:** [API.md](API.md)（共通契約）、[SPEC.md](SPEC.md)（企画背景）

---

## 0. このドキュメントの範囲

Web アプリの画面を作る。

- 現在地の入力（2セレクタ）
- 目的地の選択（碁盤の目のグリッドUI）
- 経路の指示表示

**やらないこと:** 経路計算・指示文の生成（バックエンド担当）

---

## 1. 企画の核心（これを外すと意味がない）

> **Kyoter = 観光客っぽくなく移動できる。スマホを見ながら歩かないから。**

この一文が全ての画面設計を規定する。

### 1.1 地図を出さない

**実際の地図（航空写真・道路図・地図ライブラリ）を一切使わない。**
目的地の選択も、通り名が並んだ**抽象的な格子**で行う。

地図を出した瞬間に企画が死ぬ。

### 1.2 歩いている間、画面を見せない

指示は**出発前に一覧で全部見せる**。ターンバイターンではない。

ユーザーは指示を読んで覚え、**スマホをしまって歩く**。
これが体験の本体。したがって:

- 指示は**1画面に収まる**のが理想（スクロールさせない）
- 手順数は少ないほど良い
- 覚えやすい文であること

## 2. 技術構成

| 項目 | 選択 | 備考 |
|---|---|---|
| 形式 | 素の HTML / CSS / JavaScript | **ビルド不要。**アイデアソンなので最短で動く形 |
| フレームワーク | 使わない | 必要と判断すれば相談 |
| 通信 | `fetch` で `/api/*` を叩く | |

日本語のみ（SPEC 3.1）。スマホ画面前提のレイアウト。

### 2.1 バックエンドを待たずに開発する

`mock/grid.json` と `mock/route.json` を読んで開発を進めること（API.md 5.1）。

最初からデータ取得部分を差し替え可能にしておき、
最後に fetch 先をモックから `/api/*` に切り替える。

## 4. 画面

> **4.1 と 4.2 は同じ画面に並べる。**
> 現在地のセレクタを変えると、グリッド上の現在地マーカーが追従する。

### 4.1 現在地の入力

**ユーザーは交差点まで移動し、その交差点を選ぶ**（SPEC 4.7）。GPS は使わない。

英語圏の `5th Ave × 42nd St` と同じ構造。**2つのセレクタ**で指定する。

```
┌─────────────────────────────┐
│  いま、どの交差点にいますか   │
│                             │
│   [ 縦の通り ▼ ]            │
│        ×                    │
│   [ 横の通り ▼ ]            │
│                             │
│      [ 決定 ]               │
└─────────────────────────────┘
```

要件:

| # | 要件 | 理由 |
|---|---|---|
| 1 | **選択式のみ。**自由入力は不可 | 表記ゆれ・誤字が起きない |
| 2 | 並び順は `index` 順（配列の順）。**50音順にしない** | 実際の街の並びと一致する。使ううちに通りの順番が頭に入る |
| 3 | 片方を選んだら、**もう片方を実在する通りだけに絞る** | `exists` を使う（API.md 3.1） |

> 現地の通り名標識を読んで自分の位置を知る ── この動作自体が体験の一部。

### 4.2 目的地の選択（グリッドUI）

**碁盤の目を模した抽象的な格子**を表示し、そこから選ぶ（SPEC 4.5）。

```
      A   B   C   D   E
   ┌───┬───┬───┬───┬───┐
 1 │   │   │   │   │   │
   ├───┼───┼───┼───┼───┤
 2 │   │   │ ● │   │   │   ● = 現在地
   ├───┼───┼───┼───┼───┤
 3 │   │ ★ │   │   │   │   ★ = 選択中の目的地
   ├───┼───┼───┼───┼───┤
 4 │   │   │   │ ✕ │   │   ✕ = 存在しない交差点
   └───┴───┴───┴───┴───┘
```

要件:

| # | 要件 |
|---|---|
| 1 | 縦軸・横軸に通り名を表示する |
| 2 | `exists` が false の交差点は選べないことが**見て分かる** |
| 3 | 現在地を明示する |
| 4 | 京都タワーの位置を表示する（方角の理解を助ける） |
| 5 | 通りの本数が変わっても崩れないこと（**本数をハードコードしない**） |
| 6 | 主要な通り（`major`）を強調し、実際の街の見え方に近づける |
| 7 | 観光地（`spots`）を表示する（下記） |
| 8 | **通りの幅と街区の広さを見た目に反映する**（下記） |

> 実データでは 洛中で 縦横それぞれ数十本になる。スマホ画面で破綻しないこと。

#### 街の形を反映する

均等な格子にしない。実際の京都は通りの幅も街区の広さもばらばらで、
そこが「碁盤の目」の見え方を作っている。

| データ | 見た目 |
|---|---|
| 隣り合う `pos` の差（街区の広さ） | マスの大きさ |
| `width`（通りの幅） | 罫線の太さ |

御池通・堀川通・五条通（幅50m）は太く、六角通・蛸薬師通（幅5m）は細くなる。
京都御苑の南北（今出川通〜丸太町通・約1.1km）は他の街区より広く空く。

> 距離をそのまま画素にすると御所の南北が街区の9倍になり画面に収まらない。
> 平方根で圧縮したうえで上下限を設けること。

#### 観光地の表示

観光客が行きたいのは「三条 × 河原町」ではなく「錦市場」。
通り名を知らなくても目的地を選べるようにする（SPEC 4.5.4）。

| 表現 | 内容 |
|---|---|
| チップ | グリッドの上に観光地名を並べる。押すとその交差点が目的地になる |
| 印（◉） | `spot.at` の交差点に置く |
| 淡い塗り | `spot.area` の範囲（京都御苑・二条城・京都駅など） |

目的地が観光地なら、要約に「錦市場（錦小路通 × 寺町通）」のように名前を添える。

### 4.3 経路の指示（最重要画面）

**この画面が製品の本体。** ユーザーはこれを読んで覚え、スマホをしまう。

```
┌─────────────────────────────┐
│  F通 × 12通  →  C通 × 8通    │
│                             │
│  ① 京都タワーを背にして      │
│     4本上ル（8通まで）       │
│                             │
│  ② 京都タワーを右手に見て     │
│     3本東入ル（C通まで）      │
│                             │
│  ─────────────────          │
│  [ 覚えた。歩きます ]         │
│  [ ギブアップ ]              │
└─────────────────────────────┘
```

#### 目印の方を向いた景色（`scene.js`）

指示文の上に、**その場に立って目印の方を見た景色**を線画で出す
（docs/SPEC.md 2.6 段階C）。

```
      ／＼        ← 山の稜線
 ┌─┐        ┌──┐
 │ │  ┌──┐  │  │   ← 建物（PLATEAU LOD1 を透視投影）
```

- `route.start.scene.url` の SVG を `<img>` で読むだけ。**フロントで描画しない**
- 線画があるのは **319 / 479 交差点（67%）**。目印が一点として定まる所だけ
- 無いときは帯を出さず、文章の指示（`hint`）だけで歩いてもらう

> **なぜ方位帯をやめたか。**「東に山が見えます」だけでは三方が山の京都では
> 絞れない。見回すと複数の方角に山があり、どれが東か分からない。
> **形を見せれば実景と一致させられる。**

要件:

| # | 要件 | 理由 |
|---|---|---|
| 1 | **`instruction` をそのまま表示する。**フロントで文を組み立てない | 表現をバックエンドに集約する（API.md 3.2） |
| 2 | 全手順を1画面に出す | 出発前に覚えるため |
| 3 | 手順番号を大きく、覚えやすく | |
| 4 | **タワーが見えない手順が分かるようにする** | `tower_visible` が false の区間はユーザーが不安になる箇所 |
| 5 | 「覚えた」を押したら画面を暗くする等、**スマホをしまう動作を促す** | 企画の核心（1.2） |

#### 経路候補の切り替え

`routes` は複数返る（先頭が推奨）。切り替えて見せてもよい。

その際は `visible_ratio`（タワーが見える割合）と `turns`（曲がる回数）を
選択の手がかりとして出す。

#### ギブアップ

押すと地図が出る ＝ **観光客に戻る**、というコンセプト上の敗北条件（SPEC 2.3）。
v1 では画面だけ用意して、実装は最小でよい。

### 4.4 到着の答え合わせ — **スコープ外**

> **やらない。** 歩行中の「着いた」で最初の画面に戻るだけにする。
>
> バックエンドには `POST /api/arrival` が実装済みだが、**画面からは呼ばない**。

## 5. トーン

- 京都らしさは**指示文**に出る（バックエンドが生成）
- 画面自体は**静かで、余白があり、読みやすい**方がよい
- 派手な装飾より、**指示が一目で頭に入ること**を優先する
